Projeto Integrador — Fiscalização de Velocidade sem Radar

Ricardo Pasquati Pontarolli

Técnico em Redes de Computadores · IFSP Boituva · pasquati@ifsp.edu.br · v7

Objetivos desta aula

  • Modelar o banco de dados que vai guardar as leituras de velocidade do projeto
  • Sair do requisito → modelo conceitual → modelo lógico → modelo físico → SQL
  • Instalar e configurar o SGBD no próprio Raspberry Pi, via container
  • Colocar o banco do grupo no ar, cada integrante com sua própria entrega

No 1º semestre a turma já praticou SQL no Neon (Postgres gerenciado na nuvem). Agora, no 2º semestre, a persistência do projeto passa a rodar localmente no Raspberry Pi, via Docker — reforça a ideia de “nó de borda” (o dado processado e guardado no mesmo lugar, sem depender de um serviço externo) e cobre o item da ementa “instalação e configuração de um SGBD”, que o Neon (já pronto, gerenciado por terceiros) não exercitava.

Mudança deliberada nesta versão da aula: em turmas anteriores, com uma única entrega por grupo, era comum 2 de 5 integrantes não participarem. A atividade de hoje foi dividida em 5 papéis com entrega individual rastreável por commit — ver bloco “Mão na massa”.

Recapitulando o projeto

  • A prefeitura quer saber se os veículos ultrapassam o limite de velocidade, sem instalar radares
  • Cada grupo simula um veículo (carro, ônibus, patinete elétrico…) rodando uma rota fixa de trechos com limite
  • O Raspberry Pi (nó de borda) já roda Docker, Portainer e o broker MQTT (de CNVI)
  • Hoje: depois que a leitura for comparada com o limite, onde ela fica guardada?

Onde entra o Banco de Dados

  • Sem persistência, cada leitura se perde assim que chega — não dá pra provar nada depois
  • O banco de dados guarda: o veículo, a legislação das vias, a rota de cada um e cada leitura registrada
  • É a partir dele que se responde: “quantas infrações o ônibus do grupo 3 cometeu na rota simulada?”

Nota

No roteiro-mestre do projeto, a Aula de Persistência aparece com banco de série temporal (InfluxDB). Optamos por um banco relacional (PostgreSQL) neste módulo — é o que a ementa de Banco de Dados exige (modelo ER, modelo relacional, SQL/DDL/DML) e o volume de leituras da simulação não precisa de um banco de série temporal de verdade.

Levantamento de requisitos

Antes de desenhar qualquer tabela, perguntar: o que o banco precisa responder?

  • Quais são as características do meu veículo (marca, modelo, teto de velocidade)?
  • Qual a legislação de cada tipo de via (limite legal daquele trecho)?
  • Qual é a rota do meu veículo — em que ordem ele passa por cada via?
  • Qual foi a velocidade em cada leitura, e ela foi uma infração ou não?
  • Quantas infrações o veículo cometeu, no total e por trecho?

Essas cinco perguntas já bastam para chegar às quatro entidades do modelo conceitual — e, não por acaso, cada uma delas vira o papel de um integrante do grupo daqui a pouco. Vale perguntar à turma antes de revelar o próximo slide: “que entidades vocês tirariam dessas perguntas?”

Modelo Conceitual — as entidades

  • Veículo — o veículo simulado pelo grupo (marca, modelo, tipo, teto próprio, se houver)
  • Via — um tipo de via e o limite de velocidade definido por lei para ela (local, coletora, arterial…)
  • Trecho — um passo da rota fixa do veículo: qual via, em que ordem
  • Leitura — um registro de velocidade em um instante, em um trecho, de um veículo

Nota

Reparem que a regra de negócio do veículo (limite normal / teto próprio / via restrita) não vira uma 5ª entidade — ela é lógica aplicada na hora de calcular limite_aplicado, cruzando via.limite_legal com veiculo.teto_proprio. O banco guarda o resultado, não a regra em si.

Modelo Conceitual — Entidade-Relacionamento

Do Conceitual ao Modelo Lógico

Regras de mapeamento ER → Relacional aplicadas aqui:

  • Toda entidade vira uma tabela, todo atributo vira uma coluna
  • Relacionamento 1:N vira chave estrangeira do lado “N”
  • Trecho depende de Veículo e de Via → duas FKs na mesma tabela
  • Leitura depende de Veículo e de Trecho → duas FKs na mesma tabela
  • Cada tabela precisa de uma chave primária — aqui, um id autoincremental

Modelo Lógico — as tabelas

Tabela Chave primária Chaves estrangeiras Papel dono
veiculo id — Integrante 1
via id — Integrante 2
trecho id veiculo_id, via_id Integrante 3
leitura id veiculo_id, trecho_id Integrante 4

Essa é a tabela que vai virar o CREATE TABLE direto, sem surpresas — o modelo lógico já é praticamente o esqueleto do DDL. A coluna “papel dono” já antecipa a divisão de trabalho de daqui a pouco.

Modelo Físico — escolha do SGBD

  • Modelo físico = decisões concretas de implementação: qual SGBD, quais tipos de dado, índices, etc.
  • Vamos usar PostgreSQL, mesma sintaxe que vocês já praticaram no Neon — só que agora rodando em container, no Raspberry Pi
  • Um Postgres por Raspberry Pi, compartilhado entre os grupos daquele nó — cada grupo com seu próprio banco e usuário

Por que um Postgres compartilhado, não um container por grupo?

  • O RPi 3B+ tem só 1 GB de RAM, já dividido entre Docker, Portainer, Mosquitto e o microsserviço Moleculer de cada grupo que usa aquele nó
  • Um Postgres ajustado (buffers pequenos) roda tranquilo nesse espaço — oito Postgres (um por grupo) espalhados em 5 nós, não
  • Um único Postgres atendendo vários bancos é o mesmo modelo do Neon (um serviço multi-tenant) — só que rodando na borda, não na nuvem de terceiros
  • É também o mesmo padrão que vocês já usam nos tópicos MQTT: infraestrutura compartilhada, cada grupo identificado pelo seu próprio nome/veículo

Instalação e configuração — Docker Compose

services:
  postgres:
    image: postgres:16-alpine
    container_name: postgres-fiscalizacao
    restart: unless-stopped
    environment:
      POSTGRES_PASSWORD: "combinada-em-sala"
    volumes:
      - pgdata:/var/lib/postgresql/data
    ports:
      - "5432:5432"
    command: >
      postgres -c shared_buffers=16MB
               -c max_connections=20
               -c work_mem=4MB
volumes:
  pgdata:

Nota

Suba isso pelo Portainer (Stacks → Add stack), do mesmo jeito que já fizeram com o Mosquitto. Os parâmetros -c reduzem o consumo de memória do Postgres, que por padrão reservaria bem mais RAM do que o RPi tem sobrando. Se o Postgres do seu nó já existir (outro grupo subiu primeiro), pulem direto para o próximo passo.

Cada grupo cria o seu banco

-- conectar como superusuário (postgres) uma única vez
CREATE DATABASE fiscalizacao_onibus;
CREATE USER onibus WITH PASSWORD 'senha-do-grupo';
GRANT ALL PRIVILEGES ON DATABASE fiscalizacao_onibus TO onibus;
  • Depois disso, todo mundo do grupo conecta em fiscalizacao_<veiculo>, como o usuário do próprio grupo — não mais como superusuário
  • Isso é literalmente o item da ementa “instalação e configuração de um SGBD” — feito por vocês, não por um provedor de nuvem

SQL — DDL x DML

  • DDL (Data Definition Language) — define a estrutura: CREATE TABLE, ALTER TABLE, DROP TABLE
  • DML (Data Manipulation Language) — manipula os dados: INSERT, SELECT, UPDATE, DELETE
  • Hoje: cada papel escreve o DDL da sua tabela e o DML que a popula — a visão geral é esta:

DDL — véiculo e via (papéis 1 e 2)

-- Integrante 1
CREATE TABLE veiculo (
    id            SERIAL PRIMARY KEY,
    grupo         VARCHAR(50) NOT NULL,
    marca         VARCHAR(30),
    modelo        VARCHAR(30),
    tipo          VARCHAR(30) NOT NULL,
    teto_proprio  NUMERIC(5,2)          -- NULL = sem teto próprio
);

-- Integrante 2
CREATE TABLE via (
    id            SERIAL PRIMARY KEY,
    tipo_via      VARCHAR(30) NOT NULL UNIQUE,
    limite_legal  NUMERIC(5,2) NOT NULL
);

DDL — trecho (papel 3)

-- Integrante 3 (só roda depois que 1 e 2 já existirem)
CREATE TABLE trecho (
    id          SERIAL PRIMARY KEY,
    veiculo_id  INTEGER NOT NULL REFERENCES veiculo(id),
    via_id      INTEGER NOT NULL REFERENCES via(id),
    ordem       INTEGER NOT NULL,
    UNIQUE (veiculo_id, ordem)
);

DDL — leitura (papel 4)

-- Integrante 4 (só roda depois que trecho já existir)
CREATE TABLE leitura (
    id               SERIAL PRIMARY KEY,
    veiculo_id       INTEGER NOT NULL REFERENCES veiculo(id),
    trecho_id        INTEGER NOT NULL REFERENCES trecho(id),
    registrado_em    TIMESTAMPTZ NOT NULL DEFAULT now(),
    velocidade       NUMERIC(5,2) NOT NULL,
    limite_aplicado  NUMERIC(5,2) NOT NULL,
    infracao         BOOLEAN GENERATED ALWAYS AS
                        (velocidade > limite_aplicado) STORED
);

Nota

infracao é uma coluna gerada: o Postgres calcula sozinho, a cada linha, se velocidade > limite_aplicado. Ninguém precisa lembrar de calcular isso na hora de inserir.

DML — inserindo dados de teste

INSERT INTO veiculo (grupo, marca, modelo, tipo, teto_proprio)
VALUES ('Turma A - Grupo 3', 'Marcopolo', 'Viale', 'onibus', 90);

INSERT INTO via (tipo_via, limite_legal) VALUES
  ('local', 40), ('coletora', 60), ('arterial', 80);

INSERT INTO trecho (veiculo_id, via_id, ordem) VALUES
  (1, 1, 1), (1, 2, 2), (1, 3, 3);

INSERT INTO leitura (veiculo_id, trecho_id, velocidade, limite_aplicado) VALUES
  (1, 1, 38, 40),
  (1, 2, 65, 60),   -- infração
  (1, 3, 95, 80);   -- infração

DML — respondendo as perguntas do início (papel 5)

-- infrações por veículo
SELECT v.grupo, v.tipo, count(*) FILTER (WHERE l.infracao) AS infracoes
FROM veiculo v JOIN leitura l ON l.veiculo_id = v.id
GROUP BY v.grupo, v.tipo
ORDER BY infracoes DESC;

-- velocidade média por tipo de via
SELECT va.tipo_via, avg(l.velocidade) AS vel_media
FROM leitura l
JOIN trecho t ON t.id = l.trecho_id
JOIN via va ON va.id = t.via_id
GROUP BY va.tipo_via;

Acesso em modo texto — psql

psql -h rpi-102.local -U onibus -d fiscalizacao_onibus
\dt                        -- lista as tabelas
SELECT * FROM veiculo;
  • Funciona do terminal do seu PC (mesma rede Wi-Fi i4 do RPi) ou via SSH direto no nó
  • Troque rpi-102.local pelo hostname do nó do seu grupo

Acesso em modo gráfico

  • DBeaver ou pgAdmin — clientes gráficos gratuitos, instaláveis no PC
  • Conexão: host rpi-10X.local, porta 5432, banco fiscalizacao_<veiculo>, usuário do grupo
  • Vantagem do gráfico: ver a estrutura das tabelas, editar linhas na mão, montar consultas com autocomplete

Acesso por uma aplicação

import psycopg2

conn = psycopg2.connect(
    host="rpi-102.local", dbname="fiscalizacao_onibus",
    user="onibus", password="senha-do-grupo",
)
cur = conn.cursor()
cur.execute(
    "INSERT INTO leitura (veiculo_id, trecho_id, velocidade, limite_aplicado) "
    "VALUES (%s, %s, %s, %s)",
    (1, 2, 63.5, 60),
)
conn.commit()

Nota

É exatamente esta chamada — em Node.js, não Python — que o microsserviço de CNVI (Moleculer) vai fazer depois de comparar velocidade x limite. E agora o destino é o próprio Raspberry Pi: o nó de borda processa a leitura e grava no banco que roda ali do lado, sem depender de um serviço externo na internet.

Mão na massa — um banco, cinco papéis

  • O banco é um só por grupo — mas cada integrante tem uma tabela (ou etapa) sob sua responsabilidade
  • Cada papel entrega o seu próprio arquivo .sql, com commit no seu próprio nome/usuário GitHub
  • Papéis iguais para todos os grupos — só os dados mudam (ônibus, moto, patinete…); a estrutura da atividade é a mesma

Nota

A avaliação de hoje é por papel, não só por grupo: quem não tiver o próprio arquivo .sql commitado com seu nome não pontua nessa entrega, mesmo que o banco do grupo esteja funcionando.

Antes dos papéis — infraestrutura do grupo

  1. Descubram qual RPi (rpi-102 a rpi-106) é o nó do seu grupo
  2. Confiram se o Postgres já está rodando nele (Portainer → Containers). Se não estiver, subam a stack do slide anterior
  3. Conectem como superusuário e criem o banco + usuário do grupo (CREATE DATABASE, CREATE USER, GRANT)
  4. Anotem host, porta, nome do banco e usuário — vão precisar disso nos 5 papéis a seguir

Os 5 papéis

Papel Integrante Entrega Arquivo
1 — Veículo características do veículo (marca, modelo, teto) CREATE TABLE veiculo + 1 INSERT sql/01_veiculo.sql
2 — Legislação limite legal de cada tipo de via da rota CREATE TABLE via + INSERTs sql/02_via.sql
3 — Rota sequência de vias que o veículo percorre CREATE TABLE trecho + INSERTs sql/03_trecho.sql
4 — Leituras leituras simuladas de velocidade CREATE TABLE leitura + INSERTs sql/04_leitura.sql
5 — Consultas & Acesso agregações + testar os 3 tipos de acesso sql/05_consultas.sql + README.md —

Grupos com menos de 5 integrantes: combinar papéis próximos (ex.: 1+2, ou 4+5), mas sempre deixando claro no README quem assumiu o quê — a rastreabilidade por commit continua valendo.

Ordem de execução

  1. Juntos (5 min): infraestrutura do slide anterior (banco + usuário do grupo criados)
  2. Papéis 1 e 2, em paralelo: cada um escreve e roda seu CREATE TABLE + INSERT, conectado como usuário do grupo
  3. Papel 3: só começa depois que 1 e 2 rodaram (precisa dos ids gerados por eles)
  4. Papel 4: só começa depois que 3 rodou
  5. Papel 5: roda as consultas, testa psql + cliente gráfico + o script Python, e escreve o README.md

Checklist de entrega de cada papel (todos em paralelo desde já):

  1. Repositório fiscalizacao-<veiculo>-db criado, com todos os integrantes do grupo + pontarolli como colaboradores
  2. Cada integrante escreve seu arquivo em sql/0N_<papel>.sql (DDL + INSERTs da sua tabela)
  3. O grupo roda os 4 scripts na ordem (1→2→3→4) no banco fiscalizacao_<veiculo> do RPi
  4. Papel 5 roda as 2 consultas de agregação e testa psql + cliente gráfico + o script Python de acesso
  5. Papel 5 escreve o README.md: schema, papéis, quem fez o quê (nomes), host/porta/banco — sem senha
  6. Cada integrante faz commit + push do seu próprio arquivo, com seu próprio usuário GitHub

Entrega de hoje

  • Repositório fiscalizacao-<veiculo>-db com os 5 arquivos em sql/, cada um commitado pelo integrante responsável
  • README.md com a tabela de papéis preenchida (papel → nome) e os dados de conexão (host/porta/banco, sem senha)
  • Print (ou saída copiada) da consulta de infrações rodando no banco do RPi (papel 5)

Nota

Sem tempo de terminar tudo? Priorizem os papéis 1 a 4 rodando no banco (estrutura completa) — papel 5 pode fechar consultas e README em casa, mas cada arquivo .sql precisa existir com o commit de quem o fez.

Como cada grupo já tem um repositório do projeto (de CNVI), vale reforçar que este é um repositório novo e separado, só para a parte de banco — fiscalizacao-<veiculo>-db — não um branch do repositório de infraestrutura.

Circular entre os grupos durante o bloco “papéis 1 e 2 em paralelo” — é o momento mais fácil de identificar quem está só observando o colega digitar, em vez de escrever o próprio arquivo.

Boas práticas que já valem desde hoje

  • Nunca commitar a senha do banco em nenhum .sql ou no README.md
  • Guardar a senha em variável de ambiente (ou arquivo .env fora do git)
  • Cada arquivo sql/0N_*.sql só com o DDL/DML da tabela daquele papel — não misturar

Nota

A senha combinada em sala e compartilhada entre os grupos do mesmo nó é uma simplificação proposital para dar suporte em aula — igual ao usuário pi/senha 147 do próprio Raspberry Pi. Em um sistema de verdade, cada grupo (ou aplicação) teria credenciais só suas.
