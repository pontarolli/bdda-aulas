Objetivos desta aula

  • Modelar o banco de dados que vai guardar as leituras de velocidade do projeto
  • Sair do requisito → modelo conceitual → modelo lógico → modelo físico → SQL
  • Colocar o banco do grupo no ar e testar os três jeitos de acessá-lo (texto, gráfico, aplicação)

Esta é a aula de Banco de Dados dentro do projeto integrador que vocês já conhecem de Computação em Nuvem e Virtualização (RPi como nó de borda) e Redes sem Fio (rede do RPi). Hoje o recorte é: onde e como os dados de cada leitura de velocidade vão ser guardados, de forma que dê pra consultar depois quem cometeu quantas infrações.

Recapitulando o projeto

  • A prefeitura quer saber se os veículos ultrapassam o limite de velocidade, sem instalar radares
  • Cada grupo simula um veículo (carro, ônibus, patinete elétrico…) rodando uma rota fixa de trechos com limite
  • O Raspberry Pi (nó de borda) recebe as leituras de velocidade via MQTT e compara com o limite do trecho
  • Hoje: e depois que a leitura foi comparada — onde ela fica guardada?

Onde entra o Banco de Dados

  • Sem persistência, cada leitura se perde assim que chega — não dá pra provar nada depois
  • O banco de dados guarda: os veículos, a rota de cada um (trechos e limites) e cada leitura registrada
  • É a partir dele que se responde: “quantas infrações o ônibus do grupo 3 cometeu na rota simulada?”

Nota

No roteiro-mestre do projeto, a Aula de Persistência aparece com banco de série temporal (InfluxDB). Optamos por um banco relacional (PostgreSQL) neste módulo — é o que a ementa de Banco de Dados exige (modelo ER, modelo relacional, SQL/DDL/DML) e o volume de leituras da simulação não precisa de um banco de série temporal de verdade.

Levantamento de requisitos

Antes de desenhar qualquer tabela, perguntar: o que o banco precisa responder?

  • Qual é a rota do meu veículo, e qual o limite de cada trecho dela?
  • Qual foi a velocidade em cada leitura, e o veículo estava em qual trecho?
  • Aquela leitura foi uma infração ou não?
  • Quantas infrações o veículo cometeu, no total e por trecho?

Essas quatro perguntas já bastam para chegar às entidades do modelo conceitual. Vale perguntar à turma antes de revelar o próximo slide: “que entidades vocês tirariam dessas perguntas?”

Modelo Conceitual — as entidades

  • Veículo — o veículo simulado pelo grupo (tipo, teto próprio de velocidade, se houver)
  • Trecho — um pedaço da rota fixa do veículo (tipo de via, limite daquele trecho, posição na rota)
  • Leitura — um registro de velocidade em um instante, em um trecho, de um veículo

Nota

Reparem que a regra de negócio (limite normal / teto do veículo / via restrita) não vira uma 4ª entidade — ela já foi resolvida no microsserviço de CNVI antes do dado chegar aqui. O banco só guarda o resultado: qual era o limite aplicado naquela leitura.

Modelo Conceitual — Entidade-Relacionamento

Do Conceitual ao Modelo Lógico

Regras de mapeamento ER → Relacional aplicadas aqui:

  • Toda entidade vira uma tabela, todo atributo vira uma coluna
  • Relacionamento 1:N (Veículo → Trecho, Veículo → Leitura, Trecho → Leitura) vira chave estrangeira do lado “N”
  • Leitura depende de Veículo e de Trecho → duas FKs na mesma tabela
  • Cada tabela precisa de uma chave primária — aqui, um id autoincremental

Modelo Lógico — as tabelas

Tabela Chave primária Chaves estrangeiras
veiculo id —
trecho id veiculo_id → veiculo.id
leitura id veiculo_id → veiculo.id, trecho_id → trecho.id

Essa é a tabela que vai virar o CREATE TABLE direto, sem surpresas — o modelo lógico já é praticamente o esqueleto do DDL.

Modelo Físico — escolha do SGBD

  • Modelo físico = decisões concretas de implementação: qual SGBD, quais tipos de dado, índices, etc.
  • Vamos usar PostgreSQL, gerenciado pelo Neon (neon.com) — free tier, Postgres na nuvem, sem instalar nada localmente
  • Cada grupo cria seu próprio banco no Neon (um projeto por grupo)

Por que não Postgres local no Raspberry Pi?

  • Os 5 Raspberry Pi já são compartilhados por 8 grupos — rodar 8 bancos locais no mesmo RPi disputaria RAM/disco com o Docker/MQTT de CNVI
  • Um banco gerenciado na nuvem é exatamente o tipo de decisão de infraestrutura que a prefeitura tomaria de verdade
  • O RPi continua no papel de nó de borda: ele processa a leitura e envia o resultado para o banco, não guarda os dados localmente

Nota

Isso não impede testar Postgres local em container via Portainer como exercício à parte (fica combinado com o professor de CNVI) — mas o banco oficial do grupo, que vale a entrega de hoje, é o do Neon.

SQL — DDL x DML

  • DDL (Data Definition Language) — define a estrutura: CREATE TABLE, ALTER TABLE, DROP TABLE
  • DML (Data Manipulation Language) — manipula os dados: INSERT, SELECT, UPDATE, DELETE
  • Hoje: primeiro o DDL (criar as 3 tabelas), depois o DML (popular e consultar)

DDL — criando as tabelas

CREATE TABLE veiculo (
    id            SERIAL PRIMARY KEY,
    grupo         VARCHAR(50) NOT NULL,
    tipo          VARCHAR(30) NOT NULL,
    teto_proprio  NUMERIC(5,2)          -- NULL = sem teto próprio
);

CREATE TABLE trecho (
    id          SERIAL PRIMARY KEY,
    veiculo_id  INTEGER NOT NULL REFERENCES veiculo(id),
    ordem       INTEGER NOT NULL,
    tipo_via    VARCHAR(30) NOT NULL,
    limite_via  NUMERIC(5,2) NOT NULL,
    UNIQUE (veiculo_id, ordem)
);

DDL — a tabela de leituras

CREATE TABLE leitura (
    id               SERIAL PRIMARY KEY,
    veiculo_id       INTEGER NOT NULL REFERENCES veiculo(id),
    trecho_id        INTEGER NOT NULL REFERENCES trecho(id),
    registrado_em    TIMESTAMPTZ NOT NULL DEFAULT now(),
    velocidade       NUMERIC(5,2) NOT NULL,
    limite_aplicado  NUMERIC(5,2) NOT NULL,
    infracao         BOOLEAN GENERATED ALWAYS AS
                        (velocidade > limite_aplicado) STORED
);

Nota

infracao é uma coluna gerada: o Postgres calcula sozinho, a cada linha, se velocidade > limite_aplicado. Ninguém precisa lembrar de calcular isso na hora de inserir.

DML — inserindo dados de teste

INSERT INTO veiculo (grupo, tipo, teto_proprio)
VALUES ('Turma A - Grupo 3', 'onibus', 90);

INSERT INTO trecho (veiculo_id, ordem, tipo_via, limite_via) VALUES
  (1, 1, 'local',    40),
  (1, 2, 'coletora', 60),
  (1, 3, 'arterial', 80);

INSERT INTO leitura (veiculo_id, trecho_id, velocidade, limite_aplicado) VALUES
  (1, 1, 38, 40),
  (1, 2, 65, 60),   -- infração
  (1, 3, 95, 80);   -- infração

DML — respondendo as perguntas do início

-- infrações por veículo
SELECT v.grupo, v.tipo, count(*) FILTER (WHERE l.infracao) AS infracoes
FROM veiculo v JOIN leitura l ON l.veiculo_id = v.id
GROUP BY v.grupo, v.tipo
ORDER BY infracoes DESC;

-- velocidade média por tipo de via
SELECT t.tipo_via, avg(l.velocidade) AS vel_media
FROM leitura l JOIN trecho t ON t.id = l.trecho_id
GROUP BY t.tipo_via;

Acesso em modo texto — psql

psql "postgresql://usuario:senha@ep-xxxx.neon.tech/neondb?sslmode=require"
\dt                        -- lista as tabelas
SELECT * FROM veiculo;
  • O Neon mostra essa string de conexão pronta no painel do projeto
  • Funciona do terminal do seu PC ou do próprio Raspberry Pi via SSH

Acesso em modo gráfico

  • SQL Editor do Neon — direto no navegador, sem instalar nada, já vem com o projeto
  • DBeaver ou pgAdmin — clientes gráficos instaláveis, mesma string de conexão do psql
  • Vantagem do gráfico: ver a estrutura das tabelas, editar linhas na mão, montar consultas com autocomplete

Acesso por uma aplicação

import psycopg2

conn = psycopg2.connect(
    "postgresql://usuario:senha@ep-xxxx.neon.tech/neondb?sslmode=require"
)
cur = conn.cursor()
cur.execute(
    "INSERT INTO leitura (veiculo_id, trecho_id, velocidade, limite_aplicado) "
    "VALUES (%s, %s, %s, %s)",
    (1, 2, 63.5, 60),
)
conn.commit()

Nota

É exatamente esta chamada — em Node.js, não Python — que o microsserviço de CNVI (Moleculer) vai fazer depois de comparar velocidade x limite. Hoje vocês testam a peça isolada; nas próximas aulas ela se conecta ao resto do pipeline (MQTT → microsserviço → banco).

Mão na massa — o banco do seu grupo

Agora, em grupo, coloquem o banco de dados do projeto no ar:

  1. Criar repositório fiscalizacao-<veiculo>-db no GitHub (ex.: fiscalizacao-carro-db)
  2. Criar um projeto/banco Postgres gratuito em neon.com
  3. Ajustar o modelo ER às particularidades do seu veículo e da sua rota (roteiro do Projeto 01)
  4. Escrever schema.sql com o DDL das 3 tabelas e rodar no SQL Editor do Neon
  5. Inserir dados de teste: seu veículo, os trechos da rota, pelo menos 5 leituras (com 1+ infração)
  6. Rodar as duas consultas de agregação (infrações por veículo, velocidade média por trecho)
  7. Testar o acesso via psql a partir do terminal
  8. Criar README.md documentando as tabelas — sem a senha do banco
  9. Adicionar pontarolli como colaborador do repositório
  10. commit + push de schema.sql, dos inserts de teste e do README.md

Entrega de hoje

  • Link do repositório fiscalizacao-<veiculo>-db, com schema.sql versionado
  • Print (ou saída copiada) da consulta de infrações rodando no Neon
  • pontarolli como colaborador do repositório

Nota

Sem tempo de terminar tudo? Priorizem 1–7 (banco criado, schema, dados, consultas rodando) — README e colaborador podem fechar em casa, mas o commit de hoje precisa existir.

Como cada grupo já tem um repositório do projeto (de CNVI), vale reforçar que este é um repositório novo e separado, só para a parte de banco — fiscalizacao-<veiculo>-db — não um branch do repositório de infraestrutura.

Boas práticas que já valem desde hoje

  • Nunca commitar a senha do banco no schema.sql ou no README.md
  • Guardar a string de conexão em variável de ambiente (ou arquivo .env fora do git)
  • schema.sql só com DDL (estrutura) — os INSERTs de teste podem ir num arquivo separado, ex. dados_teste.sql
